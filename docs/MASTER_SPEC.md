# 第二部分：完整产品定位

## 2.1 产品愿景

打造一个面向康复医疗机构的 AI Operations Platform。

将以下工作连接在统一产品中：

患者咨询 → 信息理解 → 知识检索 → 服务质检 → 意向预约 → 工单创建 → 人工审批 → 客户跟进 → 运营分析 → 自动化评测。

最终效果：

让用户看到 AI 不只是回答问题，而是在受控范围内真正参与企业业务流程。

## 2.2 核心使用角色

至少设计四种业务角色：

1. 客服 / 康复顾问
2. 门诊运营管理人员
3. 治疗师 / 医疗专业人员
4. 系统管理员

支持独立 Demo 角色切换以展示不同视图。

真正的权限控制必须在服务端执行；如果角色切换仅为演示，不得冒充生产级登录认证。

## 2.3 设计原则

- 实用优先
- 面向真实业务
- AI 能力可解释
- Agent 调用可追踪
- 人工始终具有最终控制权
- 数据状态真实变化
- 演示数据与真实数据明显区分
- 医疗决策不能由 AI 自主执行
- 所有核心模块共享数据库与业务对象
- 产品可扩展、可维护、可测试

## SYSTEM 03 — AI Communication Quality & Safety Agent

这是产品的重要差异化能力。

目标：辅助检查客服回复是否存在不当承诺、错误或遗漏。

### 检测项目

- 缺乏依据的医疗判断
- 不当治疗效果保证
- 未经验证的保险报销承诺
- 未经核实的预约可用性
- 错误的院区信息
- 错误的服务信息
- 未回答用户核心问题
- 缺少必要的人工确认
- 不专业或含糊的表达
- 与知识库资料相冲突

### 输出结果

每次质检生成：

- 风险分类
- 风险等级
- 涉及的具体句段
- 检测理由
- 引用的业务规则或知识来源
- 建议修改方案
- 可供人工审核的回复草稿

如果证据不足，明确输出“无法核实”。

不要将质检分数包装为医疗监管部门认可的合规认证。

支持规则引擎和真实 LLM 辅助审查。

界面分别显示规则审查结果与模型判断，避免让用户误以为所有判断都有同等确定性。

## Scenario A：双语预约意向处理

输入：

“我跑步后膝盖不舒服，想预约前滩门诊，最好周六上午。我有商业保险，可以英语沟通吗？”

系统：
